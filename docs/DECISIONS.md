### D21 Bake pipeline and sources
`npm run bake` (`tools/bake/index.ts`): fetch (cached in the gitignored `.cache/bake`), build (`tools/bake/build.ts`, pure), write `public/data/` last through temp files and renames, so a blocked host or a crash never leaves half output. The Natural Earth commit is looked up once with `git ls-remote https://github.com/nvkelso/natural-earth-vector.git HEAD` (result `ca96624a56bd078437bca8184e78163e5039ad19`, the same as the prompt's fallback); later bakes read the SHA from the committed `public/data/meta.json` so a rebake stays reproducible even if upstream HEAD moves (`--ne-sha=` overrides). Natural Earth files: `ne_50m_admin_0_countries`, `ne_10m_populated_places_simple`, `ne_10m_ports` (geojson). Terrarium z4: 256 tiles, 18 345 644 bytes. `--synthetic` swaps in seeded noise and boxes, writes only to `.cache/bake-synthetic`, and `bake:check` rejects a `public/data/meta.json` without a real commit SHA. Node's built-in fetch worked in the sandbox without `NODE_USE_ENV_PROXY`.

### D22 Determinism and checksums
No timestamps anywhere; JSON keys sorted; countries ordered by descending area; cities by population; ports by cell. gzip level 9 (memLevel 9) with the header normalised (mtime 0, XFL 2, OS 255). `public/data/checksums.json` = `{version, packs: {name: {file, bytes, sha256, fnv1a, gzBytes, gzSha256, layers: {name: {offset, bytes, sha256, fnv1a}}}}, files: {json name: {bytes, sha256, fnv1a}}}`. `sha256` and `fnv1a` (8 hex digits) are over the UNCOMPRESSED payload and authoritative (`bake:check`, Node tests, and the browser loader checks `fnv1a`, which is pure TS and needs no secure context); `gzSha256` is informational because the deflate stream can differ between Node/zlib versions (`bake:check` prints a note, never fails on it). `public/data/manifest.json` and `public/data/checksums.json` themselves are not checksummed. Two bakes in a row gave byte-identical files (see `docs/PROGRESS.md`).

### D23 Pack layout (`src/data/format.ts`, shared by the baker and the loader)
Two packs. `render` (18 874 368 bytes raw): `height` u8 4096x2048, `bathy` u8 2048x1024, `country` u8 4096x2048. `sim` (4 816 896 bytes raw): Int16 layers first (2-byte aligned, little endian): `meanElev`, `maxElev` (1024x512), `navMaxElev` (256x128); then u8 `land`, `class`, `country`, `coast`, `ruggedness` (1024x512) and `navFlags` (256x128). Offsets are in `public/data/meta.json` (`render.layers`, `sim.layers`) and `public/data/checksums.json`. One render pack (as the prompt says) instead of one file per raster.
Sqrt coding: `metres = max * (code / 255)^2`, land max 9000 m, depth max 11000 m. Code 0 = no land / no water. The smallest code that decodes to at least 1 m is 3 ((3/255)^2 * 9000 = 1.25 m; code 2 gives 0.55 m), so `MIN_LAND_CODE = 3` for heights and depths (the prompt said "code 1"; that would decode to 0.14 m).
Terrain class numbers: DeepSea 0, Shallows 1, Plains 2, Forest 3, Hills 4, Mountain 5, Peak 6, Ice 7. `coast` bits: 1 = land cell next to water, 2 = water cell next to land (8-neighbourhood, longitude wraps). Nav grid (4 x 4 sim cells per nav cell): `navFlags` bits AnyLand 1, AllLand 2, AnyRough (Mountain or Peak) 4, AnyIce 8, AnyCoast 16, plus `navMaxElev`; the prompt did not define the nav contents, this is the minimal useful set. `meta.sim.cosQ15[row]` = round(cos(lat of the row centre) * 32768) for the 512 sim rows (value 32768 near the equator does not fit an Int16, store it as Uint16 or clamp).

### D24 Heights
Terrarium decode `R*256 + G + B/256 - 32768`. Clean on the 4096x4096 Mercator grid BEFORE any mean or max: clamp to [-11000, 9000] (2 pixels were above 9000: the 11 500 m error pixels near 72.4 N 78.8 W), then a 3x3 median (longitude wraps) replaces a pixel only when it deviates more than `SPIKE_MEDIAN_DEVIATION_M = 2000` m from the median: 65 pixels (the Baffin Island error cluster, a few Greenland and Baffin coast pixels, Pacific atoll pixels sitting in deep ocean, a few seamount tops); real peaks survive (Himalaya box max 6727 m before and after). Resampling to the 4096x2048 equirectangular grid: columns line up 1:1, rows are weighted by latitude overlap (area correct), per pixel mean and max. The 56 rows at each pole beyond the Mercator limit (85.0511 degrees) are synthetic: the nearest real row smoothed along longitude with a box of +-32 columns (`POLAR_SMOOTH_COLUMNS`); the polar streaks are visible in the height map (Antarctica interior is Ice anyway). Natural Earth polygons are authoritative for land; land pixels are forced to >= 1 m and sea pixels to <= -1 m.

### D25 Rasteriser (`tools/bake/raster.ts`)
Own scanline fill, pixel centres, half-open row interval (no double counting at vertices), all rings of a feature together under even-odd (holes and islands in lakes come out right whatever the winding). A ring with a longitude jump over 180 degrees is unwrapped and drawn three times (-360, 0, +360) clipped to the grid; edges that run along a pole (Antarctica's closing edge from +180 to -180 at -90) are not treated as jumps. The 50m Natural Earth file has no ring with a jump (already split at +-180), so the real bake never needed the unwrapping; unit tests cover it.

### D32 World units, camera model and limits
One world unit is one Earth radius (6371 km); the sphere is at radius 1 and the terrain is displaced radially by `HEIGHT_EXAGGERATION * height / 6 371 000`. The camera is described by the focus point on the SEA-LEVEL sphere (lat, lon), `heading` (compass bearing the camera looks toward, 0 = north up), `tilt` (0 = straight down, limit 72), and `distKm` = distance from the camera to the focus point (limits 220 and 42 000 km). Up, right and forward come from the analytic east / north frame, so they are defined at the poles. Interaction: left drag grabs the globe (the sphere point under the cursor follows the cursor; heading is locked, so north stays up), release gives inertia (angular velocity, time constant 0.45 s, no fling after a pause of 80 ms), wheel zoom eases in log space (time constant 0.12 s) and keeps the point under the cursor fixed EXACTLY (the look direction is rotated rigidly with the focus, so the heading may change a little, the small roll of a trackball), right drag or ctrl/shift drag turns heading and tilt. While interacting the focus latitude is limited to +-88 degrees (heading locked to north would spin wildly closer to the pole); `setView` accepts +-90 and stays finite (tests at both poles for every heading and tilt). Near and far planes follow the distance. The camera looks at sea level, not at the displaced surface (a mountain-centred focus is in the backlog).

### D33 Sun and time
The sun is a pure function of the fx time `t` (seconds): declination `SUN_DECLINATION_DEG` = 14, sub-solar longitude `SUN_LON_AT_T0_DEG - 360 t / SUN_DAY_SECONDS` (it moves west, one day per 1800 s). `__test.setView({time})` sets the fx clock to `time` seconds; `timeForSubsolarLon(lon)` gives the time for a wanted sub-solar longitude (used by the canonical views and by tests that must put a city on the night side). The prompt left the unit of `time` open; the fx clock is the only clock, so `time` is fx seconds. All of this is in `src/render/config.ts` and `src/render/geo.ts`.

### D34 Terrain shader decisions (`src/render/shaders/terrain.ts`)
- Heights are filtered LINEARLY on the sqrt code by the vertex shader and by `HeightField.heightM` (same maths, so CPU picking matches the picture). The fragment shader never trusts the filtered texture for the COAST: land is a bilinear blend of the binary mask (code 0 = sea) read with `texelFetch`, thresholded at 0.5 with a `fwidth` ramp, so the coast follows the 4096x2048 raster and not the coarse mesh. Land height and sea depth use normalised convolution (land-only and water-only texels), so the coast neither sinks to 0 nor lifts the water.
- Biome tone: cubic B-spline over 4 x 4 sim class cells, land cells only. A plain bilinear mix showed the 4 x 4 block pattern of the baked Forest/Plains rule as a checkerboard.
- Shading normal = slope normal of the exaggerated height field at the resolution of the raster (central differences, step at least 1.5 raster pixels and 1.5 screen pixels, so it does not shimmer when zoomed out) plus the mesh facet normal from `dFdx` and `dFdy` of the displaced position, weighted by `FACET_WEIGHT` = 0.5. The prompt asks for derivative flat shading; on its own it only shows the coarse mesh (156 km facets at the test tier) and Himalaya and Alps looked like smooth blobs.
- Snow line `mix(6900, 1300, smoothstep(8, 65, |lat|))` metres (about 5300 at 28 N, 2750 at 46 N); the first values made the whole Tibetan plateau white.
- Water colour from bathymetry depth: turquoise at the coast to deep blue below 6500 m. Lighting is done in linear space (albedo to the power 2.2, result to the power 1/2.2); ShaderMaterial does no colour conversion by itself. No mipmaps (R8 data textures, LinearFilter).
- Shader modules: `src/render/shaders/common.ts` and `src/render/shaders/terrain.ts` now; the ocean and atmosphere modules belong to item 3 (checkpoint B). The country-id texture exists and is read back in tests, but no shader samples it before item 4.

### D39 Atmosphere (`src/render/shaders/atmosphere.ts`)
One single-scattering function, `atmosphereScatter(ro, rd, tMax, sun, steps)`, serves two consumers: the terrain fragment shader (6 steps from the camera to the surface point: haze and the glow on the disc near the limb) and the back-face additive shell (10 steps, a 96x48 sphere of radius `ATMOSPHERE_TOP` = 1.07 Earth radii, `BackSide`, `AdditiveBlending`, depth test on, no depth write, drawn after the opaque globe). Density falls with `exp(-altitude / ATMOSPHERE_SCALE_HEIGHT)` (0.011 radii, stylised: the real shell is 1.016 and would be a hairline at globe scale); sunlight at each sample is blocked when the sun ray passes inside the unit sphere (soft edge), the colour goes from blue to orange-red as the sun gets low, the result is `radiance + transmittance`. The shell works with the camera inside it (the closest zoom is 220 km). The lit factor is a `max` of two smoothsteps so that it is continuous across the terminator: a hard `up > 0` step drew a visible line on the sea at dusk (found in a screenshot). Numbers are in `src/render/config.ts`.

### D40 Ocean (`src/render/shaders/ocean.ts`)
Eight plane waves on the sphere (wave numbers 260 * 1.75^i per radian, i.e. 154 km down to 3 km), slope 0.065 for the largest and 0.8x per octave, a slow phase warp breaks the crests. Every octave fades out by its period in PIXELS (`smoothstep(16, 56)`), so zoomed out the sea has no stripes or moire and the glint is a smooth patch; the first version (fade at 9..28 px) striped the whole sea at 8000 km. The time is the fx clock, so in `?test=1` the normals are frozen without an extra switch. Fresnel (`OCEAN_F0` = 0.02, power 5) mixes the lit water body with a sky colour (horizon to zenith by the reflection angle, night sky at night); the glint has a broad lobe (strength 0.6, exponent 45) and a tight lobe (1.8, 900), both gated by the sun being above the local horizon.

### D41 Country borders and the palette LUT (`src/render/shaders/borders.ts`, `src/render/palette.ts`)
Four taps of the NEAREST country id texture at +-0.7 pixel (screen-space derivative of the DIRECTION, not of the uv, so there is no seam at the antimeridian): a pixel is on a border when neighbours have a different NON-ZERO id; id 0 (sea) never counts, so coast against sea is no border. ### D42 Night lights (`src/render/nightLights.ts`)

## M03 Sim foundation (determinism, intents, host seam)

### D51 Ticks, turns and the T + 2 schedule (`src/sim/rules.ts`, `src/sim/time.ts`)
`state.tick` counts completed steps (u32). A `Turn` is the tick at whose step its intents run; in M03 one turn is one tick, so `Tick` and `Turn` are the same number (two names so that a later turn spanning several ticks changes the call sites, not the meaning). An intent submitted while the state is at tick T runs in the step that starts at tick T + `INTENT_DELAY_TURNS` (2): `scheduledTurn(T)`. `step(state, {turn, intents})` runs exactly the turn `turn === state.tick`; anything else is an error RESULT (`turn-mismatch`, `bad-turn`, `too-many`) that leaves the state untouched, so the caller, never the sim, decides what a missing or late turn means (lockstep waits, a replay stops). `rules.ts` holds only `TICK_HZ` 10, `TICK_MS` 100, `INTENT_DELAY_TURNS` 2, `MAX_INTENTS_PER_TURN` 4096 and `MAX_TICKS_PER_FRAME` 8; a test checks that everything it exports is a UPPER_SNAKE_CASE constant. The structural limits that follow from the array types (`MAX_SEATS` 255 because ownerId is a Uint8, `MAX_DIMENSION` 4096, `MAX_CELLS` 2^22) live in `src/sim/state.ts` and are not tunables. `ENGINE_VERSION` (state.ts, 1) must be bumped with any change of a rule or a constant in rules.ts; snapshots of another engine version are refused.

### D52 State layout and the match header (`src/sim/state.ts`)
Structure of arrays, parameterised by (width, height): `terrain` Uint8, `elevation` Uint16, `owner` Uint8 (ownerId, 0 = unowned), `stamp` Uint32 (id of the intent that last painted the cell), `rng` Uint32Array(4), and the integers `tick` and `rejects`. Header `{engineVersion, mapHash, seed, config, seats}` plus width and height. `mapHash` defaults to the hash of terrain and elevation (a real match passes the pack checksum). `config.debugIntents` is the only option; it travels as a flag word and a snapshot with unknown flag bits is refused. `seatToOwner` / `ownerToSeat` / `NO_OWNER` / `NO_SEAT` are the ONLY conversion (a source test scans src for `seat + 1` and `owner - 1` outside state.ts). `STATE_ARRAY_NAMES` is the fixed order for hash and serialisation; a test lists every typed array on a state and fails when one is missing from the registry, and a per-array test flips one byte (and the top bit of the last word) and demands another hash. `terrain` and `elevation` never change in M03; `stamp` exists so that the id tie-break is visible in the state (and the hash), not only in the order of events.

### D53 The hash (`src/sim/hash.ts`)
FNV-1a over 32-bit words, in a fixed order: header words, scalars, the generator, then terrain, elevation, owner, stamp, each with its length first; narrow arrays are packed little-endian by shifts (never through a typed-array view). Deviation from the plain algorithm: after every word the state is folded with `h ^= h >>> 15`. Reason, shown by a test: plain word-wise FNV-1a only moves bits upward, so a change in bit 31 stays in bit 31 and two such changes in different words cancel exactly (an owner byte of 128 or more in two places would go unseen). The fold keeps the property that a single changed word always changes the result (every step is a bijection). The hash is 32 bits: a false match is 1 in 4.3 billion per comparison, which suffices for tests and for per-turn desync detection; M26 may want a second 32-bit lane (BACKLOG). `hex32` prints it.

### D54 Random numbers (`src/sim/rng.ts`)
sfc32 with the state in `state.rng`, seeded by four splitmix32 outputs and 12 discarded draws; both checked against an independent BigInt implementation for 1000 draws and pinned with literal values for seeds 0 and 1. `nextBelow(rng, n)` is unbiased by rejection sampling and uses exact integer `%`. `step()` draws ONCE per tick even when nothing happens, so the stream position is part of the hash from tick 1 and a snapshot that forgot the generator would be caught by the snapshot-and-resume property; M04 rules draw from the same stream after that call.

### D55 Q15 sin / cos table (`tools/gen/lut.ts`, `src/sim/sinLut.ts`, `src/sim/detmath.ts`)
Angle unit: 1/65536 of a turn (u16, wraps). The table is a quarter wave of 1025 entries (1024 steps, so 4096 steps per turn), `round(sin(i / 4096 turns) * 32768)` in a `Uint16Array` (the top entry 32768 = 1.0 does not fit an Int16). The 4 low bits of the angle interpolate linearly. Measured over all 65536 angles against `Math.sin` / `Math.cos`: the largest error is 0.983 Q15 units (asserted <= 1); the sine of the quarter turns is exact. `npm run gen:lut` writes the file, `tests/sim/lut.test.ts` regenerates the text and demands byte equality. Negative values are made as `0 - x`, not `-x`: the test of the quarter turns caught `-0` coming out of `-(0)`. `isqrt32` is bitwise (no float at all), `isqrt` uses the exactly rounded `Math.sqrt` plus integer correction and is checked against BigInt up to 2^52. `floorDiv` is exact for safe integers (remainder first, then an exact division).

### D56 Intents (`src/sim/intents.ts`, `src/sim/step.ts`)
Only `Noop{seat}` and `DebugPaint{seat, cell}` exist (DebugPaint is valid only when `config.debugIntents`); every intent also has an `id` (u32). M04 replaces both with Spawn and Attack and must APPEND to `INTENT_KINDS` (the index is the wire code). Inside a turn intents run in the order (seat, id, kind, payload) after validation; a second intent with the same (seat, id) is refused as a duplicate, and which copy survives does not depend on the input order (the one that sorts first). `validateIntent(unknown, ctx)` is total and returns a reason code; an invalid intent is a no-op that adds one to `state.rejects` (u32, wraps) and one reject event to the outbox. The ids come from an `IdAllocator` (one counter per seat, from 0): the host hands them out, so the UI submits bodies without ids. There is no replay protection across turns yet (BACKLOG). The first two turns of a match are empty by construction, because nothing submitted at tick 0 can run before tick 2; the golden script respects that, which is why a host-driven run and a direct run of the script are the same run.

### D57 Codec (`src/sim/codec.ts`)
Intent = kind u8, seat u8, id as unsigned LEB128, cell as LEB128 (DebugPaint only); turn = turn varint, count varint, intents. Varints are accepted in their shortest form only, so every accepted byte string has one meaning and re-encodes to itself (a property test over random bytes). Decoding is total and returns `{ok:false, error, offset}`; a count above `MAX_INTENTS_PER_TURN` or larger than the remaining bytes can hold is refused before anything is allocated. The decoder checks only what the bytes can show; whether a seat or cell exists is step()'s verdict. Encoding throws `RangeError` for values the wire cannot hold (a sender-side programming error). Sizes: Noop 3 bytes, small DebugPaint 4, largest 12.

### D58 Outbox (`src/sim/outbox.ts`)
`state.outbox` is NOT part of the state: not hashed, not serialised, never read by step(); three tests (hash with junk in it, bytes with junk in it, a full outbox changing nothing). It holds `Paint` (cell, ownerId) and `Reject` (reason) events, is capped at 8192 events (`dropped` counts the overflow) and is drained by the host after every step, which is also where the diff stream comes from. M03 allows at most 4096 paints per step, but M04 will exceed the cap; the host therefore reads `dropped` and falls back to a full resync (D69).

### D59 Serialisation (`src/sim/serialize.ts`)
Layout in the file header (60 byte header, 8 bytes per cell, a 4 byte checksum), little-endian through `DataView`, so the bytes do not depend on the machine. The checksum is `hashState` of the parsed state, which makes EVERY single flipped bit of a snapshot detectable (tested for all 1024 bits of a small snapshot and for sampled positions of a large one); a hostile snapshot is also range checked (seats, dimensions before any allocation, ownerId <= seats, exact length). `deserialize` returns `{ok:false, error}` and never throws; the arrays it returns are copies (a Node Buffer's `slice` would share memory, so `set(subarray)` is used). `FORMAT_VERSION` 1.

### D60 The golden hashes (`e2e/goldens/sim-hashes.json`, `src/sim/scenario.ts`)
One scripted run (seed 1, the 128x64 fixture world of `src/sim/fixture.ts` built from `Math.imul` hash noise and an exact integer division by 15, 4 seats, debug intents on) is hashed at ticks 1, 10, 100, 1000 and 6000. ### D62 The Float64 canary (`src/sim/canary.ts`)

### D63 Host seam (`src/host/`)

### D68 A snapshot is a resume point of the host (`src/host/protocol.ts`, `src/host/mainThreadHost.ts`, `src/sim/intents.ts`)
Intent ids are written into `state.stamp`, so the per-seat id counters of the host are part of the hashed history, and the intents of turns T and T + 1 exist only in the host. A host rebuilt from `deserialize(bytes).state` alone therefore diverged from the straight run (measured on the audit's script: tick 6000 hash differed; counters alone were not enough either). Chosen design (a of the audit's two options): `Snapshot.resume = {idNext: Uint32Array(255), pending: [{turn, intents}]}`, plain structured-cloneable data next to `bytes`, produced by `requestSnapshot()` and consumed by `MainThreadHost.resume(snapshot, options)`, which returns null (never throws) when the bytes do not deserialize, the tick or hash disagree with them, or the resume part has the wrong shape (counter array length, turns below the tick, repeated or unordered turns, intents without a numeric id); the intents inside are refused by `step` like any other input. `IdAllocator` takes initial counters and has `counters()`. Option b (ids from the turn and the index in the sorted turn) was rejected: it would change the meaning of `stamp` and every golden, and ids must stay what a client can predict when it submits. The resume part is NOT inside the checksummed `serialize()` bytes (those stay the state alone, `FORMAT_VERSION` 1), so a durable store (M26 rejoin, M24a restart after a crash) keeps the two together as one `Snapshot` object; `tests/host/resume.test.ts` proves "snapshot at tick k, resume, run on" equals the golden for k in 1, 2, 3, 17, 999, 2501 and 3000, also through `RemoteHost` and `LocalTransport`, and that dropping either part diverges.

### D69 The ownership diff no longer depends on the outbox cap (`src/host/mainThreadHost.ts`, `src/host/protocol.ts`)
`StateDiff.cells/owners` are built from the capped, render-only outbox, which drops silently when more than 8192 events arrive in one step; M04 (a conquest of 100 000 cells in a tick, enclave flips) and the M05 ownership texture would have lost cells with no signal. Chosen (a of the audit's two options): `runTicks` reads `outbox.dropped` before every drain and, if any step of the frame dropped events, the diff carries `fullOwner`, a copy of the WHOLE owner array after the frame, with `cells` and `owners` empty; otherwise `fullOwner` is null. A consumer replaces its mirror with `fullOwner` when it is not null (documented on `StateDiff`; `cloneEvent` and the RemoteHost transfer list copy it). The check is deliberately conservative: reject events share the cap, so a frame that only overflowed with rejects also resyncs (rare, correct, and 8 KB to 4 MB per event at most). Option b (a separate non-lossy changed-cell list in the sim) is the better answer once M04 knows the real bound of changed cells per step; it stays in the BACKLOG as the replacement for this fallback. `tests/host/resume.test.ts` overflows the outbox by 500 events, at exactly the capacity (no resync) and one above (resync), in the middle of a multi-tick frame, and across `LocalTransport`.

### D70 Tighter step budgets (`tests/sim.perf.test.ts`)
The budgets `budgetMs(1)` were about 1000 to 2500 times the measured cost of an empty step (0.4 to 0.8 microseconds) and could not tell an O(intents) step from one that scans or copies a whole array (measured: a loop over the 524 288 owner cells 330 us, `owner.slice()` 260 us, `hashState` 2.2 ms). ### D73 Units: std-cell, quarter troops, milli-gold, micro-QT (`src/sim/rules.ts`, `src/sim/units.ts`)
The plan's rules were written for a 512x256 grid; the sim runs 1024x512, so a STD-CELL is 2x2 sim cells and a number is converted by what it measures: a distance times `STD_CELL_SIDE` (2), an area times `STD_CELL_AREA` (4), a linear speed times 2, and a RATE of captured cells (cells per second, an area per time) times 4, never 2 (the plan says "omräknas till simceller x4"). The converter is the pair of constants in `src/sim/rules.ts` (it may only export `UPPER_SNAKE_CASE` constants, a source test enforces that) plus the functions of `src/sim/units.ts`. Troops are stored in QUARTER TROOPS (QT, `QT_PER_TROOP` 4): a std-cell of Plains costs `BASE_COST` 3 troops = 12 QT, a sim cell a quarter of that = 3 QT = 0.75 troop with no rounding and no ceil to whole troops; `QT_PER_TROOP` was chosen equal to `STD_CELL_AREA` so that this division is exact for any whole `BASE_COST`. Gold is stored in milli-gold (`MILLI_GOLD_PER_GOLD` 1000). There are no decimal literals in `src/sim` (a source test, D61): fractions in `src/sim/rules.ts` are integers with a named scale (`CAPTURE_K_MILLI` 80 = 0.08, `REGEN_SQRT_COEF_MILLI` 350 = 0.35, `UPHILL_PER_STEP_MILLI` 250, `TERRAIN_COST_PCT` 130 = 1.3). The names therefore differ from the plan's by a suffix: calibrate `CAPTURE_K_MILLI` and `BASE_COST_TROOPS` (the plan's CAPTURE_K and BASE_COST). All maths is integer: values stay below 2^53 (a comment at each formula says why), `Math.sqrt` appears only inside `isqrt` (exactly rounded, with an integer correction) and divisions are followed by `Math.floor` or are exact. The remainder of a per-tick amount that is not a whole number of QT is carried in `troopFrac` in micro-QT (`MICRO_QT_PER_QT`), so regeneration near the cap is not truncated to zero.

### D75 The capital disc and the Spawn algorithm (`src/sim/spawn.ts`) - an ambiguity of the plan
The plan says "huvudstadsskiva med radie 8 celler", "K = START_DISC_CELLS = 197, heltalspunkter i radie-8-skivan" and, in the same breath, that the rules are ported from the 512x256 design (a std-cell is 2x2). Read through the converter, radius 8 std-cells would be radius 16 sim cells (797 integer points). Read literally, 197 is a count of the cells a Spawn claims, and a Spawn claims sim cells. Chosen (the literal reading): `START_DISC_RADIUS_CELLS` 8 and `START_DISC_CELLS` 197 are in SIM cells (about 300 000 km2 at the equator, a third of Sweden), a test recounts that 197 is the number of integer points in the disc. To switch to the converted reading change the two constants (16 and 797) and re-pin the goldens: nothing else depends on them. Algorithm: Prim-like growth from the chosen cell; a binary heap (typed arrays, no allocation per cell) holds the unowned playable cells next to the claimed region, keyed by (squared distance from the chosen cell with the x seam taken the short way, `hash2(seed, cell, salt)`, cell index); the smallest is claimed, its unowned playable 4-neighbours join. The result is the K nearest CONTIGUOUS cells in distance order, a coast or another seat's land makes it reach further out, a landmass smaller than K gives all of its cells, and ties are decided by the hash of the cell (it depends on the match seed, never on array order); in open land with K = 197 the claim is exactly the radius-8 disc (a test). Cost O(K log K), no map scan: the per-cell mark lives in `state.scratch` and is cleared through the list of touched cells.

### D76 Heights: `HEIGHT_UNIT_M` and what part B decides (`src/sim/rules.ts`)
The plan's uphill factor `1 + 0.25 * dh / 32` (capped x2) needs a unit for dh. `HEIGHT_UNIT_M` is 16 m (own choice): the cap is reached at a rise of 128 units = 2048 m between two neighbouring 39 km cells, a 1000 m step costs x1.49, a 250 m step x1.12. `state.elevation` is the mean elevation in whole metres (sea clamped to 0 by `createSimWorld`), so dh in units is `floor(rise in metres / HEIGHT_UNIT_M)` from two array reads. Part B writes the choice of the incremental definition of dh (between the attacker's source cell and the target cell, no extra data) and of the depth d (BFS depth into the defender's land, kept per front cell, capped at `D_MAX_CELLS`) here, with the reasoning; this entry only records that the constants exist and what unit they are in. The constants of the conquest are already in `src/sim/rules.ts` and `docs/BALANCE.md` with the plan's values.

### D77 Troop cap and regeneration (`src/sim/economy.ts`)
N is the owned area in std-cells, cos-weighted: `warea` (the sum of the Q15 row weights of the owned sim cells, kept by `setOwner`) divided by `STD_CELL_AREA`, as a Q15 number. `N^0.75 = sqrt(N) * sqrt(sqrt(N))` with two integer roots: `s1 = isqrt(N_Q15 * 2^15)`, `s2 = isqrt(s1 * 2^15)`, result `s1 * s2 / 2^15` (floored); against the real power the relative error is below 0.1 % for N up to 40 000 std-cells (a test, and a test of the cap against `(2000 + 120 * N^0.75)`). Cap in QT = `8000 + floor(480 * N^0.75) + 3200 * cityLevels`; a tribe's is `floor(cap / 3)`; the city levels are 0 until M09 (`cityLevels()`). Regeneration per second `max((8 + 0.35 * sqrt(T)) * (1 - T / Tmax), -MAX_DECAY)` is computed in micro-troops per second from `sqrt(T) * 1000 = isqrt(T_QT * 250000)`, multiplied by `(Tmax - T)` and floor-divided by `Tmax`, then turned into micro-QT per tick (`* 4 / 10`), a tribe's positive rate times 50 %, and clamped at `-MAX_DECAY_MICRO_QT_PER_TICK`. The plan names `MAX_DECAY` but gives no number: own choice 40 troops per second (4 per tick; at the plan's cap of 2000 an owner with three times the cap loses it in about a minute). `T` above `4 * Tmax` is treated as `4 * Tmax`, where the rate is already at the clamp (for Tmax >= 2000), so every product stays below 2^53 even for a corrupt snapshot. A tick adds the rate to `troopFrac`, moves whole QT to `troops` and keeps the remainder (0 <= remainder < 10^6); when a negative sum would take `troops` below 0 it is clamped to 0 and the remainder to 0 (T >= 0 after every deduction; `deductTroops` returns what it really took). Measured, solo start disc, equator-like weight: 1200 troops reach about 90 % of the cap after 5 minutes and stay below it. Tmax = 0 gives rate 0 (no division by zero).

### D78 Gold and the start values (`src/sim/economy.ts`)
