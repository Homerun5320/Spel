## Sim flow (M03)

Intent and turn flow, in the order a click travels:

1. UI or AI builds an `IntentBody` (`{kind, seat, ...}`, no id) and calls `host.submitIntent(body)`. The host copies it (`copyBody`), hands out the id (`IdAllocator`, one counter per seat) and files it under turn `scheduledTurn(host tick)` = T + 2. Nothing is validated here: garbage becomes an intent that `step` refuses.
2. The caller reports elapsed real time with `host.advance(dtMs)`. The `FixedStepAccumulator` turns it into whole ticks (10 Hz at 1x; speeds 0, 1, 2, 4; at most 8 ticks per call; the host reads no clock).
3. For every tick the host calls `step(state, {turn: state.tick, intents})`. `step` validates each intent (`validateIntent`; an invalid one is a no-op that raises `state.rejects`), sorts the valid ones by (seat, id, kind, payload), refuses duplicates of (seat, id), applies them (`applyIntent`: a Spawn that is legal in shape but not in the state, for example on sea or by a seat that has spawned, and an Attack without land, border or troops are refused here with their reason), runs the conquest (every attack gains progress and takes its cells, D82), the enclave pass of the bucket `tick % 20` (D86) and the economy tick, draws once from `state.rng` and increments `state.tick`. A turn that does not equal `state.tick`, is not a list or holds more than 4096 intents is an error RESULT and changes nothing.
4. The host drains `state.outbox` after each step (render-only events; not hashed, not serialised) and sums the paints of the frame into ONE `diff` event (`fromTick`, `toTick`, cells with their new ownerId, reject count; if the outbox dropped events in the frame, `cells`/`owners` are empty and `fullOwner` holds the whole owner array, which the consumer must adopt, D69); every `hashEveryTicks` it also emits a `hash` event. Each listener receives its own deep copy.
5. `host.requestSnapshot()` resolves with `{tick, hash, bytes, resume}` where `bytes = serialize(state)` and `resume` holds the host's id counters and scheduled turns; `deserialize(bytes)` gives the state back (or an error result), `MainThreadHost.resume(snapshot)` a host that continues exactly like the straight run (D68).

### Snapshot growth (M05)

What crosses the host seam, and what each part costs (all of it plain typed arrays, copied per listener, transferred over a Worker):
- `diff` event, once per `advance` that ran ticks: the changed cells and their owners (or `fullOwner`, 1 MB, after an outbox overflow) plus `diff.view`, a `ViewSnapshot` with the tick, the reject counter and the last refusal (reason, tick), the match facts and the packed per-seat statistics (8 fields x seats u32 = 832 bytes for 26 seats; `owner` and `terrain` are null here). The mirror applies it in place: no allocation, no copy of the owner array per frame.
- `requestView()`: the same `ViewSnapshot` plus FULL copies of the owner array (1 MB) and the terrain layer (0.5 MB); the page asks once at start, `ViewMirror.attach` then follows the diffs.
- `requestSnapshot()`: the whole serialised state (about 5 MB) for saving, resuming and hashing; never per frame.
A new per-seat statistic is a new block of `STAT_FIELDS` (and a new `SimView` accessor); anything bigger than a per-seat number belongs in its own request, not in the per-frame diff. The ownership TEXTURE (2 MB RGBA8) is not a host snapshot: the page keeps its own CPU copy current from the diffs and uploads it whole at most 10 times per second of fx time.

### The AI call (M05 part C)

The AI runs in the sim's own thread, never in the UI. `MainThreadHost.runTicks` does, for every tick: (1) `driverView.refresh()` (a `StateView` over the live state: the per-seat statistics are recomputed, 3 us), (2) `driver.onTick(view, submit)`, (3) `step(state, {turn, intents})` with the intents filed for this turn. `AiDriver.onTick` calls `think(view, memory, rng)` for every AI seat (seats 1 to 25) with that seat's `AiMemory` and the driver's own stream; a thought returns `[]` on nine ticks in ten, and what it returns is handed to `submit`, i.e. `host.submitIntent`, which files it under the turn T + 2 like any intent (copied, given an id per seat, validated by `step`). So the AI sees the state at the end of tick T - 1, its intent runs in the step of tick T + 2, and a refusal by the sim (an attack whose free land was taken in between) is counted in `state.rejects` like any other. The AI reads: `view.tick`, `phase`, `stats.*` per seat, `owner` and `terrainClass` (only for placing a capital), `contactLength(a, b)`, and nothing else. The page's `ViewMirror` is untouched by the AI: it follows the host's diff events like for any seat. M09 replaces the host option by the Worker-side driver of `src/host/aiDriver.ts` unchanged; the AI memory and stream are NOT yet in `HostResume` (BACKLOG).

Over a Worker (M24a) the same calls become the messages of `src/host/protocol.ts` (`submit`, `speed`, `advance`, `snapshot`, `dispose` one way; `event`, `snapshot`, `error` the other); `serveHost` runs in the worker, `RemoteHost` is the `SimHost` the page holds. Nothing in a message is a class instance, a function or a reference into the sim.

Determinism rules that hold for every file in `src/sim`: integers only (a single, labelled float kernel: `src/sim/canary.ts`); only `Math.floor`, `Math.max`, `Math.sqrt`, `Math.imul` and the other exactly rounded members; no `Map`, `Set`, `JSON`, promises or `.sort()` without a comparator; multi-byte values are written through `DataView` with an explicit byte order and hashed through shifts; the generator state is inside the state. The golden hashes in `e2e/goldens/sim-hashes.json` pin all of it.
